## Execution sequence and time budget

Use these as elapsed-time budgets from launch. Reserve the last two hours before the owner's submission for evaluation, deployment checks and writing. If the remaining time is shorter, scale the run using measured throughput and record the change. Do not sacrifice the held-out evaluation to add epochs.

1. **First 45 minutes — environment and hosting probe.** Use an isolated staging workspace with the GTX 1650 (4 GB), scratch storage, network access to the public sources, and an isolated Python environment. Verify CUDA/kernel compatibility with an actual optimizer step. In parallel with data preparation, check the proposed inference backend's Linux compatibility, model size, cold start and Vercel function limits on disposable fixtures. Prefer a small, license-compatible detector that exports to ONNX and runs inside the existing server-side Node path. One viable candidate is TorchVision SSDLite320 MobileNetV3 with a two-class head (background and crack). Validate its export/postprocessing on the installed versions. Choose the architecture once the smoke test passes.
2. **First 90 minutes — data and baseline.** Fetch the DamSegment v1 *detection* distribution. Inspect its actual class map, license, labels and sample overlays. Treat reviewed crack-free images, including exhaustively labeled spalling-only examples, as negatives. Quarantine uncertain/unlabeled images. Group related views and exact/near duplicates before a seeded train/validation/test split (aim for 70/15/15). Record source group IDs, counts, seed, hashes and split checks. Apply augmentations only to training. One dam supports a within-source pilot. Evaluate building generalization later with independent buildings. [DamSegment v1](https://doi.org/10.17632/z5z6gtt5t4.1)
3. **Next 2–4 hours — conduct the first training run.** Start from documented pretrained weights, replace the detection head, set the seed, and try batch size 1–2. Use the architecture's supported native input size. Time one epoch, save resumable checkpoints, then fit within the budget. If memory or throughput is limiting, lower batch size, freeze the backbone or use a seeded train subset and disclose the count. Reload the selected checkpoint in a fresh process. Save environment, license/credit for code and weights, commands, hardware, timings, epochs, losses and artifact hashes. Keep large inputs and checkpoints in scoped scratch or private Preview artifact storage outside Git and the deployment upload.
4. **Next hour — freeze and evaluate.** Select the checkpoint and score threshold using validation only. Before opening the test split record the numerical Preview decision rule. Suggested pilot rule: held-out photo-level crack recall at least equal to the current heuristic, box F1 strictly higher at IoU 0.50, and at most one false crack alert per reviewed negative photo on average. Require positive and reviewed negative cases and a nontrivial set of distinct test groups. Report denominators, uncertainty and any shortcomings. These are demo criteria chosen for this handoff and carry no engineering certification. Score the actual deployed crack path and heuristic on the same photos using one-to-one box matching, box precision/recall/F1, photo-level recall and raw TP/FP/FN. Report counts by source group and show representative mistakes. If test data were used to tune, disclose that and seek a fresh holdout.
5. **Integrate and exercise Preview.** For a successful trained run use its crack boxes, including a valid empty set, plus only the heuristic's corrosion/spalling suggestions. On a disabled model or genuine load/inference error use the complete heuristic, identify the fallback and its cause, and preserve the user's Gemini action. Compare original and exported predictions after resize, orientation and inverse coordinate transforms. Validate artifact checksum, label map, shape and finite coordinates; bound download/inference time and cache by immutable version. Verify concurrent reruns, reviewed findings, risk and maintenance tickets across mode switches. A fallback result must identify the method that actually ran. Begin with the flag off; enable for the Preview walkthrough if both evaluation and runtime checks pass.
6. **Last two hours — walkthrough and manuscript.** Run the project's tests, typecheck, lint and build. Exercise the deployed app while signed in on a positive, a reviewed negative, a simulated missing/corrupt artifact and an explicit Gemini request. Verify reload, rerun, reviewer edits/rejection, cold and warm latency, and flag rollback. Record URL, commit, checkpoint hash, actual scores and failures. Write the *AI Modules* and *Training Process* sections, a compact baseline/candidate table and limitations under `verification/`. If the model trains but misses a gate, retain and demonstrate its offline predictions and keep the known-good Preview path active. If training cannot finish, record commands, blocker and furthest completed step.
